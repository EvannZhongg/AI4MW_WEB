# AI4MW 开发准则

本准则用于约束 AI4MW Web 后续开发，目标是让项目能够稳定演进到 Linux 服务器部署并通过反向代理对外提供服务。它强调三件事：

- 文档必须反映真实代码状态
- 配置和安全必须优先于“临时能跑”
- 新能力接入时必须考虑公网部署后的可维护性

## 1. 真实状态优先

### 文档规则

- README 只能写“已接入并可运行”的能力，不能把仅存在于规划文档或孤立目录中的模块写成已上线
- 新增能力时，必须同时更新以下至少一项文档：
  - `README.md`
  - `docs/CONFIGURATION.md`
  - 本开发准则
- 若某模块仍处于预研或未接线状态，必须明确标记为“预留”“规划中”或“未接入”

### 对当前仓库的具体要求

- `datesheet_rag` 在接入主应用前，一律视为预留能力
- `line_build` 当前主要保存曲线提取算法服务接口文档，不应误写成本仓库内直接运行的主应用模块

## 2. 配置管理准则

### 配置来源

统一遵守：

```text
系统环境变量 > .env > config.yaml
```

### 配置分工

- `config.yaml` 只放非密钥配置
- `.env` 只放密钥和密码
- 任何 API Key、数据库密码、OAuth Secret 都不得写入代码仓库中的普通配置文件

### 扁平配置要求

当前后端和前端都使用自定义的逐行解析逻辑读取 `config.yaml`，因此：

- `config.yaml` 只能使用扁平 `KEY: value`
- 禁止使用嵌套 YAML
- 禁止引入需要完整 YAML 语义才能解析的结构

如果后续要引入正式配置库，必须前后端一起升级，避免两套解析逻辑行为不一致。

### 新增配置项时必须同时做的事

新增任意配置项时，必须同步完成：

1. 在 `config.yaml` 或 `.env.example` 中补示例
2. 在 `docs/CONFIGURATION.md` 中登记用途、默认值和是否为密钥
3. 在代码中提供合理默认值或失败提示
4. 评估该配置在 Linux 生产环境中的设置方式

## 3. 架构边界准则

### 前后端边界

- 前端只通过 HTTP 调后端，不直接访问数据库、对象存储或第三方模型服务
- 模型调用必须留在后端
- 登录态相关请求必须显式考虑 Cookie / Session / CORS / CSRF

### Django 边界

- `AI4MW_web/` 只放项目级配置、主路由、全局认证与通用视图
- `llm_agent/` 负责聊天领域模型和接口，不要把与 PDF 管线无关的逻辑继续塞回 `settings.py`
- 新业务模块应以 Django app 形式接入，不要在项目根目录堆脚本

### 预留管线接入规则

`datesheet_rag` 未来若要接入，必须一次性补齐以下边界：

- app 注册
- URL 注册
- 依赖声明
- 数据库迁移
- Worker 进程
- 对象/媒体文件目录
- 失败重试和监控策略

不允许只接一半路径，让生产环境处于“代码存在但服务不可用”的状态。

## 4. Linux 公网部署准则

### 部署方式

默认采用：

- Nginx 或 Caddy 作为公网入口
- Next.js 作为前端服务
- Gunicorn 托管 Django
- PostgreSQL 不直接暴露公网端口
- Redis、Celery、MinerU 等仅在内网开放

### 网络边界

- Django 和 Next.js 默认只监听 `127.0.0.1` 或内网地址
- 80/443 之外的服务端口不直接对公网开放
- 所有公网访问统一经由反向代理

### 域名与路径规范

推荐同域名路径转发：

- `/` -> Next.js
- `/api/` -> Django
- `/accounts/` -> Django
- `/admin/` -> Django

这样可以降低跨域、Cookie 域和 OAuth 回调配置复杂度。

### 安全基线

上线前至少满足：

- `DEBUG = False`
- `SECRET_KEY` 来自环境变量
- `ALLOWED_HOSTS` 正确配置
- `CSRF_TRUSTED_ORIGINS` 正确配置
- Cookie 开启 `Secure`
- 站点启用 HTTPS
- 日志中不输出密钥、Token、密码

### 不允许的做法

- 不要让 Django `runserver` 直接暴露公网
- 不要把 `.env` 上传到公开仓库
- 不要让前端直接持有服务端密钥
- 不要依赖“开放所有源”的 CORS 策略在公网运行

## 5. 后端开发准则

### Django 配置

- 所有生产相关设置都必须可配置，不能继续硬编码在 `settings.py`
- 新设置项必须有开发环境默认值和生产环境说明
- 对外接口返回要稳定，避免前端被字段漂移反复击穿

### 接口设计

- API 路径统一放在 `/api/` 下
- 接口变更时要考虑前端兼容性
- 错误响应必须清晰、可定位，不要只返回模糊字符串
- 流式接口变更时，必须同步验证前端 SSE 解析逻辑

### 数据模型

- 业务模型放到对应 app 内
- 任何会影响生产数据结构的改动都必须带 migration
- 需要长时间保存的业务数据与临时缓存数据要分开

### 文件与媒体

- 上传文件、生成产物、日志都不能混在代码目录里长期堆积
- Linux 部署时必须规划 `MEDIA_ROOT`、日志目录、清理策略
- 删除数据库记录时，若涉及物理文件，也要评估级联清理是否安全

## 6. 前端开发准则

### 运行时配置

- 前端环境入口以 `NEXT_PUBLIC_API_BASE` 为准
- 若部署为同域转发，优先使用公网域名而不是内网端口
- 前端不得硬编码开发机地址

### API 调用

- 尽量通过统一 API 客户端封装请求
- 需要登录态的请求必须显式带 `credentials`
- 新接口接入时必须定义清晰的数据结构，不依赖“猜字段”

### 页面与组件

- 展示态占位模块要明确标注，不要伪装成已接通真实后端
- 布局和样式调整不能破坏移动端可用性
- 修改聊天流式渲染时，必须验证 Markdown、公式和错误回退状态

### 工程化

- 尽快补齐 ESLint 配置并固定命令
- 构建失败时优先修复构建链，不要长期依赖“只在 dev 能跑”

## 7. LLM / Prompt / 第三方服务准则

### 模型接入

- 模型供应商、模型名、Base URL、温度等必须配置化
- 不能把密钥写在代码、前端、日志或文档截图中
- 第三方接口失败时必须给出可诊断错误，而不是静默吞掉
- `llm_agent` 的实现边界、skill 目录规范与多模态约束，统一遵守 `docs/LLM_GUIDELINES.md`

### Prompt 管理

- Prompt 应独立存放，不要散落在视图函数中拼长字符串
- Prompt 改动应视为行为改动，必要时更新文档
- 影响会话标题、摘要、分类等用户可见输出的 Prompt 修改，需记录版本意图

## 8. `datesheet_rag` 特别准则

由于该模块未来大概率会引入更多基础设施，接入时必须遵守以下原则：

- 先补依赖，再接 app，不要顺序颠倒
- 先补配置文档，再补环境变量，再上代码
- 先确认 PostgreSQL `pgvector`、Redis、Celery、MinerU 可用，再对外开放入口
- 所有异步任务都必须有失败状态、错误信息和重试策略
- 任务输出目录必须可追踪、可清理、可观测

## 9. 测试与校验准则

### 当前最低要求

每次合并前至少完成：

- Django 基础检查：`python manage.py check`
- 数据迁移检查：`python manage.py makemigrations --check`
- 前端构建或至少无交互 lint / type check

### 对重要改动的额外要求

以下变更必须补充更强校验：

- 认证与登录态改动
- 会话流式接口改动
- 配置系统改动
- 反向代理路径改动
- 文件上传与任务队列改动

### 测试建设方向

建议逐步补齐：

- Django 接口测试
- 聊天流式接口回归测试
- 前端关键页面的最小渲染测试
- 生产部署前的 smoke test

## 10. 提交与变更管理准则

### 提交原则

- 小步提交，避免把配置、安全、UI、业务逻辑混成一个大改动
- 变更说明要写清楚“改了什么”和“为什么改”
- 文档更新应与代码变更同批次提交

### 禁止提交的内容

- `.env`
- `.venv/`
- `node_modules/`
- 本地数据库文件
- 运行日志
- 上传文件和中间产物

### 遇到以下情况必须停下来同步

- 需要修改认证方案
- 需要变更部署拓扑
- 需要新增公网可访问入口
- 需要引入新的基础设施组件
- 需要更改配置解析规则

## 11. 生产发布检查清单

发布到 Linux 公网环境前，至少确认：

1. Django 生产配置已落地，不再硬编码关键安全项
2. 前端已完成正式构建验证
3. Nginx / Caddy 反向代理规则已验证
4. OAuth 回调地址已替换为公网 HTTPS 域名
5. `NEXT_PUBLIC_API_BASE`、`FRONTEND_URL` 或 `FRONTEND_HOST` / `FRONTEND_PORT`、后端域名配置一致
6. 数据库、日志、媒体目录有备份和清理方案
7. 如启用异步任务，Redis / Celery / Worker / 监控已到位

## 12. 一句话原则

任何新功能都必须同时回答下面四个问题，否则不要急着上线：

- 配置放在哪里
- 安全边界在哪里
- Linux 上怎么跑
- 文档是否已经同步
